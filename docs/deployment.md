# Deploying Design Drift

Frontend on Vercel, API and Postgres on Render. About 30 minutes end to end,
most of it waiting for the first Docker build.

Everything in this guide has been verified locally against the real
production image and a real Postgres, except the two steps that need your
accounts (creating the Render Blueprint and the Vercel project).

---

## What the deployment looks like

```
Browser ──▶ Vercel (static Vite bundle)
                │  fetch, with a bearer token
                ▼
            Render: design-drift-api  (Docker, Chromium inside)
                ├──▶ Render Postgres 16
                ├──▶ /data            persistent disk: screenshots, diffs
                ├──▶ Figma API        read a frame
                ├──▶ GitHub App       read a public repo (Contents: read-only)
                └──▶ Gemini/Anthropic the model calls
```

**Why the API is a Docker service and not Render's native Python runtime.**
The Production Analysis and Accessibility agents drive a real Chromium
(Playwright capture, axe-core against the live DOM). That needs the browser
binary plus its system libraries, which a buildpack-style runtime does not
provide. `infra/docker/backend.prod.Dockerfile` installs both.

**Why there is a disk.** Screenshots and diff images are written through
`StorageBackend` to the local filesystem. A container filesystem is
ephemeral, so without a disk every redeploy would leave runs in the
database pointing at images that no longer exist.

## Cost, stated plainly

| Piece | Plan | Cost |
|---|---|---|
| Vercel frontend | Hobby | $0 |
| Render Postgres | `basic-256mb` | ~$6/mo |
| Render API | `starter` (required for a disk) | $7/mo |
| Render disk | 1 GB | ~$0.25/mo |

Render's **free** instance type cannot run this: 512 MB of RAM against
Chromium's ~1 GB appetite, and no disk support. The free tier also spins
down after 15 minutes, so a visitor would wait ~50 seconds for a cold start.

The deployed demo serves **stored results** and never launches a browser, so
`starter` is enough for it. Live agent execution wants `standard` (2 GB) or
better.

## 1. Render: the API and the database

1. Push this repo to GitHub.
2. Render dashboard → **New** → **Blueprint** → pick the repo. It reads
   [`render.yaml`](../render.yaml) and proposes the database and the web
   service.
3. Fill in the values marked `sync: false`. Render will not deploy until
   each has a value:

   | Variable | Value |
   |---|---|
   | `CORS_ORIGINS` | Your Vercel URL, e.g. `https://design-drift.vercel.app`. No trailing slash, no wildcard. |
   | `GEMINI_API_KEY` | From <https://aistudio.google.com/apikey>. Free tier. |
   | `ANTHROPIC_API_KEY` | Optional. Only read when `LLM_PROVIDER=anthropic`. |
   | `FIGMA_ACCESS_TOKEN` | From Figma → Settings → Personal access tokens. |
   | `GITHUB_APP_ID` | Your GitHub App's numeric id. |
   | `GITHUB_APP_SLUG` | The slug from `https://github.com/apps/<slug>`. |

   `JWT_SECRET_KEY` is generated by Render. `DATABASE_URL` is wired from the
   database automatically.

4. **Secret file** for the GitHub App key. Service → **Environment** →
   **Secret Files** → add one named exactly:

   ```
   github-app-private-key.pem
   ```

   Paste the whole `.pem`, `-----BEGIN` line included. `render.yaml` already
   points `GITHUB_APP_PRIVATE_KEY_PATH` at `/etc/secrets/github-app-private-key.pem`.
   A path, not an env var holding the key, so the key never passes through
   anything that dumps the environment.

5. Deploy. The first build takes 8–12 minutes (it downloads Chromium).
   Migrations run from the container's start command, so there is nothing to
   run by hand.

6. Check it:

   ```bash
   curl https://<your-api>.onrender.com/api/v1/health
   # {"status":"ok","service":"design-drift-backend"}
   ```

If the service fails to start, the log will say why in one line. The startup
checks in `app/main.py` deliberately refuse to boot on a default JWT secret,
a wildcard `CORS_ORIGINS`, or an empty one, rather than starting up unsafe.

## 2. Vercel: the frontend

1. Vercel → **Add New** → **Project** → same repo.
2. Leave the framework preset alone; [`vercel.json`](../vercel.json) sets the
   build command, the output directory, and the SPA rewrite that makes
   `/login` and `/app` work on a hard refresh.
3. One environment variable:

   ```
   VITE_API_BASE_URL = https://<your-api>.onrender.com
   ```

   No trailing slash. It is baked in at build time, so changing it later
   needs a redeploy, not just a restart.
4. Deploy, then go back to Render and set `CORS_ORIGINS` to the Vercel URL
   you were given. The API rejects requests from origins it does not list.

## 3. Seed the demo

The public demo shows a **real** agent run, exported from your local
database and loaded into the deployed one. Two commands.

### Export it locally

With your local stack running and the Recipes Gallery project analysed:

```bash
cd backend

# Which runs exist, and the project id
uv run python -c "
import asyncio
from sqlalchemy import select
from app.db.session import async_session_factory
from app.models.project import Project

async def main():
    async with async_session_factory() as db:
        for p in (await db.execute(select(Project))).scalars():
            print(p.id, p.name)

asyncio.run(main())
"

# Read exactly what would be published first. This prints every finding,
# every file path, and every line of the target repo's source that the
# fixture would carry.
uv run python -m app.tools.demo_export --project-id <uuid> --check-only
```

**Read that output before continuing.** A located finding legitimately
quotes a few lines of the repository it analysed, that is the finding, but
you should see which lines those are before they go on a public URL.
`--check-only` exists so that decision is made with the text in front of
you. The checkout itself, whole files, and cloned workspaces are never
exported.

Then write it:

```bash
uv run python -m app.tools.demo_export \
    --project-id <uuid> \
    --out ../demo/recipes-gallery
```

That directory holds `fixture.json` plus the PNGs. Commit it.

### Load it on Render

Service → **Shell**:

```bash
python -m app.tools.demo_seed --fixture /app/../demo/recipes-gallery
```

Idempotent: re-running replaces the showcase account's projects rather than
adding a second copy. It refuses to run unless `DEMO_MODE=true`, since a
seeded account would otherwise be unreachable.

Then:

```bash
curl https://<your-api>.onrender.com/api/v1/demo/status
# {"enabled":true,"seeded":true,"user_name":"Design Drift Demo"}
```

Open the Vercel URL and go to `/app`. You should land in the workspace with
no sign-up, see the notice explaining what is stored and what is locked, and
find every control that would cost money disabled.

## What the demo can and cannot do

Enforced server-side, on the owner of the row rather than on the caller, so
it holds for an anonymous visitor, for the demo identity, and for a
signed-in stranger who guessed the project id.

**Readable without a sign-up**
: The project, every run, the findings, the located files and line numbers,
  the proposed patches, the verification verdict, all five images, and the
  exported patch file.

**Refused with a 403**
: Starting a run (plain or streamed), running a scan, running an AI review,
  recording a fix review, applying, verifying, and deleting the project.

Creating a project stays a **401**: that needs an account, and the demo
identity deliberately does not relax the "writes need a token" rule.

Covered by `backend/tests/test_demo_mode.py`, which drives each of those
routes and was checked by mutation, breaking the guard makes the tests fail,
and so does removing the `DEMO_MODE` check.

## Security notes

- **No secrets in the repo.** `.env` is gitignored; `render.yaml` marks every
  secret `sync: false`; the GitHub App key is a Render secret file.
- **The API refuses to start unsafe.** Default JWT secret, wildcard CORS, or
  empty CORS outside `local` is a startup error, not a log line.
- **CORS is an allowlist.** Verified: the allowed origin is echoed, another
  origin gets no `Access-Control-Allow-Origin` at all.
- **GitHub access is read-only by permission** (`Contents: read`), not merely
  by the absence of code that writes. Pushes and PRs are impossible.
- **Private repositories are deliberately not supported for LLM analysis.**
  The free-tier Gemini data terms may not protect confidential code.
- **The container runs as a non-root user** (`appuser`, uid 10001). It
  launches a browser that loads arbitrary pages, so a sandbox escape should
  not land on root.
- **Signup is rate limited per IP** (`SIGNUP_RATE_LIMIT_PER_HOUR`, default
  10). In-process, so it stops a script rather than a distributed attacker;
  moving to Redis is the next step if this ever runs on more than one
  instance.
- **Cost control.** Every model call is behind an authenticated, explicit
  action, and the demo cannot reach one. Set a spend cap on the API key
  anyway.

## Manual steps, collected

Things no amount of committed configuration can do for you:

1. Create the Render Blueprint and fill in the six `sync: false` values.
2. Upload the GitHub App private key as a secret file named
   `github-app-private-key.pem`.
3. Create the Vercel project and set `VITE_API_BASE_URL`.
4. Set `CORS_ORIGINS` on Render to the Vercel URL, after Vercel assigns it.
5. Export the demo fixture locally (reading `--check-only` first) and commit it.
6. Run `demo_seed` once in the Render shell.
7. Install the GitHub App on the repositories you want readable.
8. Set a spend cap on the Gemini or Anthropic key.

## Troubleshooting

**Service won't boot.** Read the first error in the log. The three startup
checks name the variable and what to set it to.

**CORS errors in the browser.** `CORS_ORIGINS` must match the browser's
origin exactly: scheme, host, no trailing slash. Vercel preview deploys get
their own hostnames, so add them or test on the production URL.

**Images 404 but findings load.** The disk is missing or `STORAGE_ROOT` is
not `/data`. Rows survive; the files were on an ephemeral filesystem.

**`/api/v1/projects` returns 401 on the deployed demo.** Either
`DEMO_MODE` is not `true`, or the seed has not run. `GET /api/v1/demo/status`
distinguishes the two.

**A run times out or the instance restarts mid-run.** Chromium ran out of
memory on `starter`. Move to `standard`. The demo path never launches a
browser, so this only affects live execution.

**`git apply` rejects an exported patch.** A patch rebuilt from a stored
proposal has no context lines and needs `git apply --unidiff-zero`. The
downloaded file says so in its own header.
